Iceberg's \texttt{rewrite\_data\_files} with \alert{bin-packing}: files

\begin{frame}{Compact or not? Utility is benefit minus cost}
\begin{center}
\resizebox{0.95\textwidth}{!}{%
\begin{tikzpicture}[node distance=3mm]
  \node[box, fill=cprimary!12, text width=44mm, minimum height=16mm] (B)
    {\textbf{Benefit} $B$\\[1pt]\scriptsize fewer files: less planning,\\\scriptsize fewer requests, fewer file opens};
  \node[font=\Large, right=of B] (minus) {$-$};
  \node[cost, text width=44mm, minimum height=16mm, right=of minus] (C)
    {\textbf{Cost} $C$\\[1pt]\scriptsize read and rewrite every eligible byte;\\\scriptsize compute, cluster occupancy};
  \node[font=\Large, right=of C] (eq) {$=$};
  \node[term, text width=30mm, minimum height=16mm, right=of eq] (U)
    {Utility $U$\\[1pt]\scriptsize\mdseries compact iff $U > 0$};

  \node[ann, below=1.5mm of B, text=cprimary!80!black]
    {structural: how many files disappear?\\ \textbf{this paper: predict it before compacting}};
  \node[ann, below=1.5mm of C]
    {a price list the operator knows:\\ I/O bandwidth, storage, compute};
\end{tikzpicture}}
\end{center}

\vspace{2mm}
\begin{columns}[T]
\begin{column}{0.5\textwidth}
We measure the benefit as the \alert{file-reduction ratio}
\[
  \rfc \;=\; 1 - \frac{n_{\mathrm{after}}}{n_{\mathrm{before}}} \in [0,1]
\]
\small $\rfc \approx 1$: the table collapses to a few files.
$\rfc \approx 0$: the rewrite is wasted I/O.
On the previous slide, $\rfc = 1 - 3/7 = 0.57$.
\end{column}
\begin{column}{0.46\textwidth}
\begin{block}{Two questions, asked of the metadata alone}
\begin{enumerate}
  \item \textbf{Whether:} will compaction rewrite anything at all?
  \item \textbf{How much:} what $\rfc$ will it achieve?
\end{enumerate}
\end{block}
\small The cost side is deployment-specific, so we leave it to the
operator and deliver the continuous signal needed to rank tables.
\end{column}
\end{columns}
\end{frame}

\vspace{3mm}
Every open-source scheduler fires on a fixed rule. The most thorough
automated system, AutoComp, ranks tables by hand-built traits and names
learned prediction as the next step. \alert{No published study has asked
which table metadata actually determines compaction utility.}
\end{frame}

% =============================================================
\section{Takeaways}
% =============================================================

\begin{frame}{Takeaways}
\begin{enumerate}
  \item \textbf{Whether to compact is a threshold, not a prediction.}
        \feat{max\_files\_per\_partition} $> 4$ matches a perfect XGBoost
        classifier on the test set and on TPC-H. It falls out of the
        bin-packing filter; no learned model is needed.
  \item \textbf{How much it will shrink does need a model.}
        XGBoost predicts $\rfc$ with $R^2 = 0.998$, transfers to six real
        schemas without retraining ($0.976$), and is robust to splits,
        class balance, feature subsets and model family. Two
        partition-level counts carry 95\% of the signal.
  \item \textbf{The benefit side of the utility depends on the workload.}
        Metadata-heavy queries gain ($1.19\times$); full-scan aggregations
        lose parallelism ($0.45\times$). Rank tables by predicted $\rfc$,
        then weigh the query mix.
\end{enumerate}

features; sort and z-order strategies; validation on production catalogs.

\begin{frame}{Backup: Threats to validity}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\textbf{Setup}
\begin{itemize}
  \item Synthetic UUID payloads compress differently from real
        columnar data
  \item Partition structure generated, not domain-derived;
        query patterns not modelled
  \item Spark-local execution $\neq$ distributed clusters on S3
  \item 89.3\% prevalence may inflate accuracy --- mitigated by a
        majority-class baseline, downsampling and bootstrap CIs
\end{itemize}
\end{column}
\begin{column}{0.48\textwidth}
\textbf{Scope --- not tested}
\begin{itemize}
  \item \textbf{Delete files / Merge-on-Read:} Copy-on-Write only.
        Merging delete files is a different dynamic
  \item \textbf{Sort and z-order:} bin-packing only. Their utility
        depends on the query workload, which metadata cannot see
  \item \textbf{Temporal evolution:} static snapshots; a table that is
        fine now may need compaction after the next write
  \item \textbf{One compaction target:} $k{=}4$ is tied to the
        128\,MB / 96\,MB configuration; 512\,MB would likely shift it
\end{itemize}
\end{column}
\end{columns}
\end{frame}

\begin{frame}{Backup: An operational threshold on the prediction}
\begin{columns}[T]
\begin{column}{0.5\textwidth}
Of the 2{,}121 tables that trigger compaction, only 11 (0.5\%) have
$\rfc \leq 0.5$, and tables with $\rfc \leq 0.1$ eliminate zero files on
average.

\vspace{2mm}
\begin{block}{A workable rule}
  Compact when predicted $\rfc > 0.3$: skips the four lowest-utility
  rewrites while keeping 99.8\% of the beneficial ones.
\end{block}

\vspace{2mm}
\small The exact cut-off is deployment-specific (storage cost, I/O
bandwidth, query mix); the regressor supplies the continuous signal to
set it.
\end{column}
